# รายงานตรวจสอบฟังก์ชันเว็บสำหรับระบบจองสนามกีฬา KKU SportPass

วันที่ตรวจ: 2026-09-06  
ขอบเขต: ตรวจความเหมาะสมของฟังก์ชันเว็บในฐานะ “ระบบจองสนามกีฬา” ไม่ใช่เฉพาะความพร้อม deploy  
ผลสรุป: **มีแกนหลักของระบบจองสนามแล้ว แต่ยังควรเพิ่มฟังก์ชันปฏิบัติงานจริงหลายส่วนก่อนใช้งานจริงเต็มรูปแบบ**

## บทสรุป

KKU SportPass มีฟังก์ชันหลักที่จำเป็นสำหรับเว็บจองสนามกีฬาแล้ว ได้แก่ หน้าเลือกสนาม, เลือกวันที่, เลือกช่วงเวลา, จองสนาม, ดูรายการจองของฉัน, ยืนยันสิทธิ์ก่อนใช้งาน, เช็คอินด้วย QR Code และ GPS, รวมถึงหน้า admin สำหรับจัดการสนาม เวลาเปิดบริการ วันปิดสนาม QR ผู้ดูแล แบบฟอร์ม และ analytics

ในเชิงผลิตภัณฑ์ ระบบเหมาะสำหรับใช้เป็น **MVP หรือ pilot ภายในมหาวิทยาลัย** ได้ หากมีผู้ดูแลคอยควบคุม แต่ยังไม่สมบูรณ์พอสำหรับการใช้งานจริงในระดับ production/operation เต็มรูปแบบ เพราะยังขาดฟังก์ชันที่ระบบจองสนามจริงควรมี เช่น การยกเลิกหรือเลื่อนการจอง, กฎจำกัดจำนวนการจองต่อผู้ใช้, dashboard ตารางการใช้สนามสำหรับเจ้าหน้าที่, ระบบแจ้งเตือน, payment/receipt สำหรับสนามที่มีค่าใช้จ่าย, waitlist, audit log และรายงานเชิงปฏิบัติการ

## ฟังก์ชันที่มีแล้ว

### 1. ระบบสมาชิกและเข้าสู่ระบบ

มีแล้ว:

- สมัครสมาชิกด้วยอีเมลที่อนุญาต
- เข้าสู่ระบบด้วยอีเมล/รหัสผ่าน
- รองรับ Google OAuth
- รองรับ SSONext ในระดับเริ่มต้น
- แยก user/admin
- admin route ถูกป้องกันด้วย `requireAdmin`
- user booking route ถูกป้องกันด้วย `requireAuth`

เหมาะสมกับเว็บจองสนามหรือไม่: **เหมาะสมในระดับพื้นฐาน**

ข้อควรปรับปรุง:

- เพิ่มหน้า/ระบบแก้ไขโปรไฟล์ เบอร์โทร คณะ/หน่วยงาน
- เพิ่ม reset password / forgot password
- เพิ่มการยืนยันอีเมลหรือผูกกับ SSO จริงให้ชัดเจน
- เพิ่ม policy สำหรับบัญชีถูกระงับหรือผู้ใช้ที่ผิดกฎการจอง

### 2. ระบบแสดงสนามและเลือกวันที่

มีแล้ว:

- แสดงสนามทั้งหมด
- เลือกวันที่ต้องการจอง
- filter ตามประเภทกีฬา
- มีแผนที่/โซนสนาม
- แสดงราคาและ capacity บางส่วน
- แสดงสนามที่ปิดบริการ
- แสดงช่วงเวลาว่างตามวันที่

เหมาะสมกับเว็บจองสนามหรือไม่: **เหมาะสมและเป็นจุดแข็งของระบบ**

ข้อควรปรับปรุง:

- เพิ่ม search สนามตามชื่อ
- เพิ่ม filter ตามราคา, โซน, indoor/outdoor, ความพร้อมของอุปกรณ์
- เพิ่มรายละเอียดสนาม เช่น รูปจริง, กฎการใช้สนาม, สิ่งอำนวยความสะดวก, ข้อจำกัดรองเท้า/ชุดกีฬา
- เพิ่มสถานะ “เต็มแล้วบางช่วงเวลา” ใน card หน้าแรกโดยไม่ต้องกดเข้าไป
- เพิ่มมุมมอง calendar หรือ timetable รวมทุกสนาม

### 3. ระบบจองสนาม

มีแล้ว:

- เลือกสนาม
- เลือกวันที่
- เลือก timeslot
- จองได้ตาม capacity
- ป้องกันการจองซ้ำของผู้ใช้คนเดิมใน slot เดียวกัน
- เช็ค court closure ก่อนจอง
- สถานะเริ่มต้นเป็น `PENDING`

เหมาะสมกับเว็บจองสนามหรือไม่: **ใช้งานพื้นฐานได้**

ข้อควรปรับปรุงสำคัญ:

- เพิ่มระบบยกเลิกการจองโดยผู้ใช้
- เพิ่มระบบเลื่อนวัน/เวลา หรือเปลี่ยนสนาม
- เพิ่มเงื่อนไขห้ามจองย้อนหลังและ validate date/time ฝั่ง server ให้เข้มขึ้น
- เพิ่ม booking policy เช่น จำกัดจองได้กี่ครั้งต่อวัน/สัปดาห์
- เพิ่มระยะเวลาจองล่วงหน้า เช่น เปิดจองล่วงหน้า 1-7 วัน
- เพิ่ม transaction/locking ป้องกัน race condition เมื่อหลายคนจอง slot เดียวกันพร้อมกัน
- เพิ่ม unique/constraint หรือ server-side atomic check สำหรับ capacity
- เพิ่มหมายเลขอ้างอิงการจอง
- เพิ่มประวัติการเปลี่ยนสถานะ booking

### 4. ระบบรายการจองของผู้ใช้

มีแล้ว:

- หน้า “การจองของฉัน”
- แสดงสนาม วันที่ เวลา และสถานะ
- แสดงสถานะ `PENDING`, `PRE_CONFIRMED`, `CHECKED_IN`, `CANCELLED`, `MISSED`
- กดยืนยันสิทธิ์ได้จากรายการจอง

เหมาะสมกับเว็บจองสนามหรือไม่: **เหมาะสมระดับพื้นฐาน**

ข้อควรปรับปรุง:

- แยก tab รายการที่กำลังจะมาถึง / ประวัติ
- เพิ่มปุ่มยกเลิกการจอง
- แสดง countdown ว่าเหลือเวลากี่ยืนยันสิทธิ์/เช็คอิน
- แสดงคำแนะนำชัดเจนว่าต้องไปถึงสนามเมื่อใด
- เพิ่มรายละเอียด QR/check-in status ต่อรายการ
- เพิ่มเหตุผลเมื่อ booking ถูกยกเลิกหรือ missed

### 5. ระบบยืนยันสิทธิ์ก่อนใช้งาน

มีแล้ว:

- ผู้ใช้กดยืนยันสิทธิ์จาก booking ที่เป็น `PENDING`
- มี setting `pre_confirm_open_minutes` และ `pre_confirm_close_minutes`
- มีระบบ timeout เปลี่ยน `PENDING` เป็น `CANCELLED`

เหมาะสมกับเว็บจองสนามหรือไม่: **แนวคิดดี แต่ควรปรับ logic ให้ชัดขึ้น**

ข้อควรปรับปรุง:

- ตอนนี้หน้า UI แสดงปุ่มยืนยันสิทธิ์เมื่อ booking เป็น `PENDING` โดยไม่ได้เห็น logic ฝั่ง UI ว่าปุ่มเปิดเฉพาะช่วง 10-5 นาทีก่อนเล่นหรือไม่
- ฝั่ง server ควร validate window การยืนยันสิทธิ์ให้ชัดเจน ไม่ใช่แค่อาศัย timeout
- ควรแสดง countdown และข้อความ “ยังไม่ถึงเวลายืนยัน” หรือ “หมดเวลายืนยัน”
- หากยืนยันสิทธิ์เร็วเกินไปควรปฏิเสธด้วย error ที่ชัดเจน

### 6. ระบบเช็คอิน QR + GPS

มีแล้ว:

- สแกน QR Code ด้วยกล้อง
- รับพิกัด GPS
- ตรวจระยะห่างจากสนามด้วย `gps_radius_meters`
- บันทึก `checked_in_at`, latitude, longitude, distance
- QR แบบ dynamic มี signature และอายุสั้น
- raw court id fallback ถูกจำกัดเฉพาะ non-production

เหมาะสมกับเว็บจองสนามหรือไม่: **เป็นฟีเจอร์ที่เหมาะมากสำหรับสนามจริง**

ข้อควรปรับปรุง:

- เพิ่มเงื่อนไข check-in window ให้ชัดเจน เช่น เช็คอินได้ตั้งแต่ก่อนเริ่ม 5 นาทีถึงหลังเริ่ม 10 นาที
- ปัจจุบัน query หา booking ของวันนี้ที่ `PRE_CONFIRMED` แต่ยังไม่เห็นการกรองตามช่วงเวลาที่กำลังเล่นโดยตรง
- แสดงชื่อสนาม/เวลาจองหลังเช็คอินสำเร็จให้ชัดขึ้น
- ปิดการแสดง QR payload debug ใน UI production
- เพิ่ม fallback/manual check-in สำหรับเจ้าหน้าที่กรณีกล้อง/GPS มีปัญหา
- เพิ่ม device/browser compatibility note สำหรับ iOS/Android

### 7. ระบบจัดการสนามของ admin

มีแล้ว:

- ดูสนามทั้งหมด
- เพิ่มสนาม
- ลบสนาม
- ดูจำนวน timeslot และ active booking
- ระบุประเภทกีฬา, พิกัด, capacity

เหมาะสมกับเว็บจองสนามหรือไม่: **มีพื้นฐานที่ดี**

ข้อควรปรับปรุง:

- เพิ่มแก้ไขข้อมูลสนามจาก UI ให้ครบ เช่น type, price, capacity, icon
- เพิ่มสถานะเปิด/ปิดสนามถาวรหรือชั่วคราว
- เพิ่ม upload/จัดการรูปสนามจริง
- เพิ่มจัดการ sport type/prefix จาก UI
- เพิ่มข้อมูลสถานที่ เช่น อาคาร, ชั้น, วิธีเดินทาง, เบอร์ติดต่อ
- เพิ่ม soft delete แทน hard delete เพื่อเก็บประวัติ

### 8. ระบบจัดการช่วงเวลา

มีแล้ว:

- admin เพิ่ม timeslot รายสนาม
- admin ลบ timeslot
- แสดง grouped timeslot ตามสนาม

เหมาะสมกับเว็บจองสนามหรือไม่: **เหมาะสมระดับเริ่มต้น**

ข้อควรปรับปรุง:

- เพิ่ม template เวลา เช่น จันทร์-ศุกร์ 16:00-21:00, เสาร์-อาทิตย์ 08:00-20:00
- เพิ่ม recurrence รายสัปดาห์/รายเดือน
- เพิ่ม validation ไม่ให้ช่วงเวลาซ้ำหรือ end_time ก่อน start_time
- เพิ่ม bulk create timeslots
- เพิ่ม copy schedule จากสนามหนึ่งไปอีกสนาม
- รองรับ slot duration ที่ต่างกันตามประเภทกีฬา

### 9. ระบบปิดสนาม

มีแล้ว:

- admin กำหนดปิดสนามรายวัน
- ปิดทุกสนามได้
- ระบุเหตุผลได้
- ระบบจองตรวจ closure ก่อนแสดง slot และก่อนจอง

เหมาะสมกับเว็บจองสนามหรือไม่: **เหมาะสม**

ข้อควรปรับปรุง:

- เพิ่มช่วงวันที่ปิดหลายวัน
- เพิ่มปิดบางช่วงเวลา ไม่ใช่ทั้งวัน
- แจ้งเตือนผู้ที่มี booking อยู่แล้วเมื่อมีการปิดสนาม
- ระบุประเภท closure เช่น ซ่อมบำรุง, แข่งขัน, กิจกรรมพิเศษ
- เพิ่ม workflow ย้าย/คืนสิทธิ์ให้ผู้ใช้ที่ได้รับผลกระทบ

### 10. ระบบ QR Poster

มีแล้ว:

- admin เลือกสนามเพื่อสร้าง QR
- มีหน้า preview/print poster
- ใช้ QR สำหรับเช็คอินหน้าสนาม

เหมาะสมกับเว็บจองสนามหรือไม่: **เหมาะสมและใช้งานภาคสนามได้ดี**

ข้อควรปรับปรุง:

- ระบุวันที่สร้าง/หมดอายุ/ประเภท QR บน poster
- ถ้า QR เป็น dynamic อายุสั้น ไม่เหมาะกับ poster ถาวร ควรแยก “static signed court QR” สำหรับ poster และ “dynamic QR” สำหรับหน้าจอเจ้าหน้าที่
- เพิ่ม version ของ QR secret เพื่อรองรับ rotation
- เพิ่ม audit log ว่าใครสร้าง/พิมพ์ QR เมื่อไร

### 11. ระบบแบบฟอร์มและแบบประเมิน

มีแล้ว:

- แบบประเมินความพึงพอใจ
- admin ดูสถิติ survey
- admin สร้าง dynamic forms
- public form response

เหมาะสมกับเว็บจองสนามหรือไม่: **เป็นส่วนเสริมที่ดี แต่ไม่ใช่ core booking**

ข้อควรปรับปรุง:

- เพิ่ม export CSV/Excel
- ผูกแบบประเมินกับ booking/check-in หลังใช้งานจริง
- จำกัดการตอบซ้ำ
- เพิ่ม dashboard แยกตามสนาม/ประเภทกีฬา/ช่วงเวลา

### 12. Analytics

มีแล้ว:

- จำนวนผู้ใช้
- จำนวน booking
- booking completed/missed/active
- popular courts
- cookie consent stats
- browser stats แบบพื้นฐาน

เหมาะสมกับเว็บจองสนามหรือไม่: **มีพื้นฐาน แต่ยังไม่พอสำหรับบริหารสนาม**

ข้อควรปรับปรุง:

- เพิ่ม occupancy rate ต่อสนาม/ช่วงเวลา
- เพิ่ม no-show rate รายสนาม/รายผู้ใช้
- เพิ่ม peak time heatmap
- เพิ่ม utilization รายวัน/สัปดาห์/เดือน
- เพิ่ม export report
- เพิ่ม revenue report หากมีสนามเสียเงิน
- เพิ่มเจ้าหน้าที่สามารถดู “วันนี้มีใครจองสนามไหนเวลาใด”

## ฟังก์ชันสำคัญที่ยังขาด

### Must Have ก่อนใช้งานจริงเต็มรูปแบบ

1. ระบบยกเลิกการจองโดยผู้ใช้

ควรมีเงื่อนไข เช่น ยกเลิกได้ก่อนเวลาเริ่ม 30/60 นาที และคืน slot ให้ผู้อื่นจองต่อได้

2. ระบบจำกัดสิทธิ์การจอง

ควรกำหนดได้ เช่น 1 คนจองได้ไม่เกิน X ครั้งต่อวัน/สัปดาห์ หรือห้ามจองหลายสนามเวลาเดียวกัน

3. ระบบตรวจช่วงเวลา pre-confirm/check-in ที่เข้มงวด

ควร validate ฝั่ง server ว่า confirm/check-in อยู่ใน window ที่อนุญาตจริง

4. ระบบป้องกันการจองชนกันแบบ atomic

ควรใช้ transaction/lock หรือ database constraint เพื่อป้องกันหลาย request จอง slot สุดท้ายพร้อมกัน

5. Admin daily operation dashboard

ควรมีหน้ารวมว่า “วันนี้ สนามไหน เวลาไหน ใครจอง สถานะอะไร เช็คอินหรือยัง”

6. ระบบแจ้งเตือน

ควรแจ้งเตือนก่อนถึงเวลา confirm/check-in ผ่าน email, LINE, push notification หรืออย่างน้อย in-app reminder

7. ระบบ manual override สำหรับเจ้าหน้าที่

เจ้าหน้าที่ควรสามารถเช็คอินแทน, ยกเลิก, mark no-show, ปรับสถานะ booking พร้อมเหตุผลได้

8. Audit log

ควรบันทึกว่าใครทำอะไร เมื่อไร เช่น สร้างสนาม, ลบ slot, ปิดสนาม, แก้ setting, เช็คอินแทนผู้ใช้

### Should Have เพื่อให้ระบบใช้งานดีขึ้น

1. Waitlist / queue

ถ้า slot เต็ม ผู้ใช้เข้าคิวรอได้ เมื่อมีคนยกเลิกให้แจ้งคนถัดไป

2. Payment workflow

เนื่องจากสนามบางรายการมีราคา ควรมีระบบจ่ายเงิน/แนบหลักฐาน/สถานะชำระเงิน/ใบเสร็จ หากจะเก็บเงินจริง

3. Booking details page

หน้ารายละเอียด booking เดี่ยวพร้อม QR/check-in instructions, location, policy

4. Export รายงาน

สำหรับเจ้าหน้าที่ควร export CSV/Excel ได้ เช่น รายการจองรายวัน, no-show, utilization

5. Role-based permissions

แยก super admin, staff, viewer, finance แทน admin role เดียว

6. Maintenance scheduling แบบละเอียด

ปิดเฉพาะบางช่วงเวลา และแจ้งผู้ได้รับผลกระทบ

7. Terms/policy acceptance

ให้ผู้ใช้ยอมรับกฎการใช้สนามก่อนจอง เช่น การมาสาย การยกเลิก การแต่งกาย ความรับผิดชอบ

### Nice To Have

1. แผนที่นำทางไปสนาม

เปิด Google Maps/Apple Maps จากพิกัดสนาม

2. รูปภาพสนามและ gallery

ช่วยให้ผู้ใช้เลือกสนามได้ง่ายขึ้น

3. รีวิว/คะแนนสนาม

เก็บ feedback หลังใช้งาน

4. QR staff mode

ให้เจ้าหน้าที่สแกน QR booking ของผู้ใช้ หรือค้น booking ด้วยชื่อ/รหัสนักศึกษา

5. Multi-language

ไทย/อังกฤษ สำหรับนักศึกษาต่างชาติ

## จุดที่ควรปรับปรุงด้าน UX

### หน้าเลือกสนาม

ดี:

- โครงสร้างสวยและเข้าใจง่าย
- มี filter กีฬาและเลือกวันที่
- มี map zone ช่วยนำทาง

ควรปรับ:

- แสดงจำนวน slot ว่างใน card สนาม
- เพิ่ม sorting เช่น ว่างมากที่สุด, ใกล้ที่สุด, ราคาถูกสุด
- ใช้รูปสนามจริงแทนรูป stock ซ้ำในหลายประเภทกีฬา
- เพิ่ม loading/error empty state ที่ actionable มากขึ้น

### หน้าจองสนาม

ดี:

- flow ยืนยัน booking ชัดเจน
- แสดง capacity เหลือ/เต็ม

ควรปรับ:

- แสดง policy ก่อนยืนยัน เช่น ยกเลิกได้เมื่อไร ไม่มาโดนอะไร
- ป้องกันเลือกวันย้อนหลังใน date picker
- แสดง slot ที่เต็มแยกจาก slot ที่ปิดหรือหมดเวลา
- แสดงเวลาตาม timezone ไทยให้สม่ำเสมอ

### หน้าการจองของฉัน

ดี:

- status badge ชัดเจน
- มีปุ่มยืนยันสิทธิ์

ควรปรับ:

- เพิ่ม tab upcoming/history
- เพิ่มปุ่ม cancel
- เพิ่ม countdown confirm/check-in
- เพิ่มรายละเอียดสนามและปุ่มนำทาง

### หน้าเช็คอิน

ดี:

- QR + GPS เหมาะกับสนามจริง
- มี error message เรื่องกล้อง/GPS

ควรปรับ:

- ซ่อน QR payload debug ใน production
- เพิ่ม manual input หรือ fallback code เฉพาะกรณีจำเป็น
- เพิ่มข้อความบอกช่วงเวลาที่อนุญาตเช็คอิน
- เพิ่ม retry flow ที่ไม่ทำให้ผู้ใช้สับสน

### หน้า Admin

ดี:

- มีเมนูครอบคลุมงานหลัก
- จัดการสนาม/เวลา/ปิดสนาม/QR ได้

ควรปรับ:

- ข้อความบางจุดยังไม่เข้ากับโดเมน เช่น “Command Center”, “Evreghen SOC Workspace”, “Sync Telemetry” ควรเปลี่ยนเป็นภาษางานสนามกีฬา
- เพิ่ม dashboard ปฏิบัติงานรายวัน
- เพิ่ม confirmation ที่ละเอียดขึ้นก่อนลบข้อมูลสำคัญ
- เพิ่ม search/filter ในตาราง admin

## ข้อเสนอ Roadmap

### Phase 1: ทำให้ใช้งานจริงขั้นพื้นฐานได้

- เพิ่ม cancel booking
- enforce pre-confirm/check-in window ฝั่ง server
- เพิ่ม booking quota/limit
- เพิ่ม atomic booking transaction
- เพิ่ม daily admin booking dashboard
- mount rate limiter และแก้ blocker production readiness จากรายงานเดิม

### Phase 2: ทำให้เจ้าหน้าที่บริหารสนามได้ดี

- เพิ่ม manual override พร้อมเหตุผล
- เพิ่ม audit log
- เพิ่ม export CSV/Excel
- เพิ่ม maintenance partial-day closure
- เพิ่ม notification/reminder
- เพิ่ม role staff/viewer/super admin

### Phase 3: ทำให้ระบบครบแบบบริการสาธารณะ

- เพิ่ม payment/receipt หากเก็บค่าบริการ
- เพิ่ม waitlist
- เพิ่ม feedback หลังใช้งาน
- เพิ่ม utilization analytics/heatmap
- เพิ่มรูปสนามจริงและ navigation
- เพิ่ม multilingual support

## คำตัดสิน

ระบบนี้ **เหมาะสมที่จะเป็นเว็บจองสนามกีฬาในระดับ MVP/Pilot** เพราะมีแกนสำคัญครบ ได้แก่ สนาม, วันเวลา, booking, capacity, booking status, QR/GPS check-in และ admin management

แต่ถ้าจะใช้งานจริงเต็มรูปแบบกับผู้ใช้จำนวนมาก ควรเพิ่มฟังก์ชันที่เกี่ยวกับ operation และ fairness ก่อน โดยเฉพาะ cancel booking, quota, enforce time window, atomic booking, admin daily schedule, notification และ audit log

ลำดับที่ควรทำก่อนที่สุด:

1. เพิ่มระบบยกเลิกการจอง
2. บังคับช่วงเวลา confirm/check-in ฝั่ง server
3. เพิ่ม quota/limit ต่อผู้ใช้
4. ทำ booking transaction ป้องกันจองชน
5. ทำหน้า admin ดูตารางการจองรายวัน
6. เพิ่ม notification/reminder
7. เพิ่ม audit log สำหรับ action สำคัญ
