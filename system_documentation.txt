เอกสารประกอบระบบ KKU SportPass (ระบบจองและจัดการสนามกีฬา มหาวิทยาลัยขอนแก่น)
================================================================================
วันที่จัดทำ: 11 สิงหาคม 2026
เวอร์ชัน: 1.0.0

ระบบจองสนามกีฬามหาวิทยาลัยขอนแก่น (KKU SportPass) พัฒนาขึ้นในรายวิชา CP321007 Design Thinking for Information Technology (การคิดเชิงออกแบบสำหรับเทคโนโลยีสารสนเทศ)
หลักสูตรวิทยาศาสตรบัณฑิต สาขาวิชาเทคโนโลยีสารสนเทศและนวัตกรรมอัจฉริยะ วิทยาลัยการคอมพิวเตอร์ มหาวิทยาลัยขอนแก่น 
โดยมีวัตถุประสงค์เพื่อศึกษาความต้องการและออกแบบประสบการณ์การใช้งาน ที่สอดคล้องกับพฤติกรรมของนักศึกษา บุคลากรภายในมหาวิทยาลัย และบุคคลภายนอกที่ต้องการเข้าใช้บริการ
================================================================================

0. กระบวนการคิดเชิงออกแบบ (Design Thinking Process)
--------------------------------------------------------------------------------
โปรเจกต์นี้เริ่มต้นจากการทำความเข้าใจผู้ใช้งานอย่างลึกซึ้งผ่านกระบวนการ Design Thinking โดยมีการวิเคราะห์ข้อมูลดังนี้:

0.1 Empathy Map (การทำความเข้าใจผู้ใช้)
- กลุ่มเป้าหมาย (WHO): นักศึกษามหาวิทยาลัยขอนแก่น และบุคคลทั่วไปที่ต้องการใช้สนามกีฬา
- สิ่งที่ต้องการทำ (GOAL): ต้องการดูว่าสนามว่างหรือไม่ก่อนเดินทางไปถึง, เพื่อแก้ปัญหาระบบการต่อคิวที่วุ่นวาย, ต้องการระบบที่แสดงสถานะแบบเรียลไทม์
- สิ่งที่ผู้ใช้เห็น (SEE): บางสนามมีระบบจองแต่ยังไม่มีแบบจองออนไลน์, ต้องต่อแถวเข้าใช้สนามนานมาก
- สิ่งที่ผู้ใช้พูด (SAY): "ถามคนที่อยู่บริเวณนั้นๆ เอา", "การต่อคิวไม่มีระบบ ดูวุ่นวาย", "ไม่อยากขับรถมาดูว่าต้องต่อคิวนานแค่ไหน"
- สิ่งที่ผู้ใช้ทำ (DO): ทักไปถามผู้ที่อยู่บริเวณสนาม, ต้องขับรถมาดูด้วยตัวเอง
- สิ่งที่ผู้ใช้ได้ยิน (HEAR): "ว่างมั้ย ไปดูสนามหน่อย", "วันนี้เขาซ้อมงานกันมั้ย", "มีคนใช้สนามมั้ยตอนนี้"
- ปัญหาที่พบ (PAINS): 
  - เสียค่าเดินทาง เสียเวลา
  - จัดการเวลาของตัวเองได้ยาก 
  - การรันคิวไม่เป็นระบบ คนมาก่อนไม่สนใจเพราะได้เล่นแล้ว คนมาทีหลังไม่รู้ต้องไปต่อคิวใคร
- สิ่งที่คาดหวัง (GAINS): 
  - อยากมีระบบที่เสถียร ไม่น่าสับสน
  - อยากทราบว่าเวลานี้มีคนอยู่สนามเยอะแค่ไหน 
  - อยากเช็คคิวการใช้สนามได้ง่ายๆ

0.2 Point of View (POV)
- User: นักศึกษามหาวิทยาลัยขอนแก่นที่ต้องการใช้สนามกีฬา
- Need: ต้องการให้นักศึกษาได้เช็คเวลาว่างและคิวการใช้สนามกีฬาแต่ละชนิดโดยที่ไม่ต้องเสียเวลาเดินทางมาดูสถานที่เอง
- Insight (ข้อมูลเชิงลึก): 
  - นักศึกษาไม่ทราบว่าสนามว่างหรือไม่ จึงเสียเวลาเดินไปดูด้วยตนเอง
  - ไม่มีระบบแสดงตารางการใช้สนามแบบเรียลไทม์ ทำให้เกิดความสับสนและเสียเวลา
  - นักศึกษาต้องการวางแผนการเล่นกีฬา แต่ข้อมูลการจองและเวลาว่างเข้าถึงได้ยาก
  - เมื่อไปถึงสนามแล้วพบว่ามีคนใช้อยู่ ทำให้เสียเวลาและไม่สะดวก

0.3 Pain Points (วิเคราะห์ปัญหา)
- Pain ที่เหมือนกัน: เสียเวลา, หงุดหงิด, วางแผนยาก, โดนลัดคิว
- Pain ที่ต่างกัน: เสียเงิน (เช่น ค่าเดินทาง, ค่าสนาม), บางคนคิดว่าระบบยุ่งยาก แต่บางคนคิดว่ามีเว็บไซต์แล้วสะดวกขึ้น

0.4 การแบ่งกลุ่มผู้ใช้ (User Personas)
1. กลุ่มเข้าใช้ทุกวัน: นักกีฬามหาวิทยาลัย, นักศึกษาที่เล่นกีฬาเป็นประจำ, บุคลากรที่ออกกำลังกายประจำ
2. กลุ่มเข้าใช้งานบางวัน: นักศึกษาที่ต้องการออกกำลังกายทั่วไป, กลุ่มนักเรียนที่เข้ามาเล่นในมหาวิทยาลัย
3. กลุ่มเข้าใช้งานเป็นครั้งคราว: คนที่สนใจอยากลองเล่นกีฬา
4. กลุ่มที่ไม่จำเป็นต้องจอง: คนที่ชอบวิ่ง หรือไม่ค่อยมีเวลาออกกำลังกาย

0.5 Ideation (แนวคิดการแก้ปัญหาจากการระดมสมอง)
- ฟีเจอร์ "เช็ค/ต่อสนามกีฬา": มีตารางสถานะแต่ละสนามว่าว่างหรือไม่
- ฟีเจอร์ "การจองคิว": จองเวลาและลงชื่อไว้ เมื่อผู้เล่นก่อนหน้าใช้เสร็จตามเวลาก็รันคิวต่อไป
- ฟีเจอร์ "ยืนยันการจอง": กำหนดเวลาจอง หากไม่มายืนยันภายในเวลาที่กำหนดจะหลุดจองทันที
- ฟีเจอร์ "เช็คอินด้วย QR Code & GPS": ทำ QR Code ในการสแกนเพื่อยืนยัน และบังคับเปิด GPS เพื่อตรวจสอบความถูกต้องว่าผู้ใช้อยู่ที่สนามจริง

1. ภาพรวมของระบบ (System Overview)
--------------------------------------------------------------------------------
KKU SportPass เป็นแพลตฟอร์มเว็บแอปพลิเคชันที่ออกแบบมาเพื่อยกระดับการให้บริการสนามกีฬาภายในมหาวิทยาลัยขอนแก่น 
ช่วยให้นักศึกษา บุคลากร และบุคคลทั่วไป สามารถเข้าถึงบริการสนามกีฬาได้อย่างสะดวก รวดเร็ว และเป็นระบบมากยิ่งขึ้น 
ระบบนี้แก้ไขปัญหาเดิมๆ เช่น การต่อคิวจองสนามที่ยาวเหยียด ความซ้ำซ้อนของการจอง การตรวจสอบสถานะสนามที่ยุ่งยาก 
ตลอดจนช่วยให้เจ้าหน้าที่สามารถบริหารจัดการสนามกีฬา จัดการผู้ใช้งาน และติดตามสถิติการใช้งานได้อย่างมีประสิทธิภาพสูงสุด

วัตถุประสงค์หลักของระบบ:
- เป็นศูนย์กลางในการจองสนามกีฬาของมหาวิทยาลัยขอนแก่น
- อำนวยความสะดวกในการตรวจสอบสถานะสนามว่างแบบ Real-time
- ลดภาระงานของเจ้าหน้าที่ในการจัดการคิวและการตรวจสอบผู้เข้าใช้
- สร้างมาตรฐานใหม่ด้วยระบบสแกน QR Code เพื่อยืนยันการเข้าใช้สนาม
- เก็บรวบรวมข้อมูลสถิติการใช้งานเพื่อนำไปวิเคราะห์และปรับปรุงบริการในอนาคต

กลุ่มผู้ใช้งานหลัก:
1. นักศึกษา (Student) - มีสิทธิ์เข้าถึงสนามกีฬาได้หลากหลายในราคาพิเศษหรือฟรี
2. บุคลากร (Staff) - ได้รับสิทธิประโยชน์เทียบเท่านักศึกษาในบางพื้นที่
3. บุคคลทั่วไป (Outsider) - สามารถใช้บริการได้ในราคาที่กำหนด
4. ผู้ดูแลระบบ (Admin) - เจ้าหน้าที่จัดการสนาม ควบคุมเวลา ปิดปรับปรุง และดูสถิติ

2. สถาปัตยกรรมและเทคโนโลยีที่ใช้ (Architecture & Technology Stack)
--------------------------------------------------------------------------------
ระบบถูกออกแบบด้วยสถาปัตยกรรม Client-Server แบบแยกส่วน (Decoupled Architecture) เพื่อให้ง่ายต่อการขยายขนาด (Scalability) 
และการบำรุงรักษา (Maintainability) โดยแบ่งเป็น 2 ส่วนหลักคือ Frontend และ Backend

2.1 Frontend (ส่วนติดต่อผู้ใช้งาน)
- เฟรมเวิร์กหลัก: React.js (สร้างด้วย Vite เพื่อความรวดเร็วในการคอมไพล์และขนาดที่เล็ก)
- ภาษาที่ใช้: JavaScript (ES6+), JSX
- การจัดการ CSS: Tailwind CSS (Utility-first CSS framework สำหรับออกแบบ UI ที่ยืดหยุ่น)
- แอนิเมชัน: Framer Motion (สำหรับการทำ Page Transition, Hover Effects, Micro-interactions)
- ไอคอน: Lucide React (ชุดไอคอนที่เรียบง่าย ทันสมัย และเบา)
- การจัดการ Routing: React Router DOM v6
- การจัดการ State: React Hooks (useState, useEffect, useContext)
- การเรียก API: Axios (รองรับการจัดการ Interceptor, Timeout, Headers)
- เครื่องมือเสริม: html2canvas (สำหรับแปลง DOM เป็นรูปภาพ เช่น การพิมพ์ QR Code)

2.2 Backend (ส่วนประมวลผลเซิร์ฟเวอร์)
- สภาพแวดล้อม: Node.js
- เฟรมเวิร์กหลัก: Express.js
- การจัดการฐานข้อมูล: PostgreSQL (ผ่านไลบรารี pg) 
- การยืนยันตัวตน: Passport.js (รองรับ Local Strategy, Google OAuth20)
- ความปลอดภัยรหัสผ่าน: bcrypt (สำหรับ Hash รหัสผ่านระดับสูง 10 rounds)
- การจัดการ Session: express-session
- ระบบ Environment: dotenv

2.3 Database (ฐานข้อมูล)
- ระบบจัดการฐานข้อมูล: PostgreSQL (เชื่อมต่อผ่าน Connection String)
- โครงสร้าง: Relational Database

2.4 การ Deploy (การติดตั้งและใช้งานจริง)
- Frontend: Vercel (CI/CD อัตโนมัติเมื่อมีโค้ดผลักเข้า GitHub)
- Backend: Vercel Serverless Functions / Node.js Hosting
- Database: Supabase / Neon / Render (PostgreSQL Cloud)

3. แนวทางการออกแบบ UX/UI (UX/UI Design Guidelines)
--------------------------------------------------------------------------------
ระบบ KKU SportPass ให้ความสำคัญกับประสบการณ์ผู้ใช้ (UX) เป็นอย่างมาก โดยเน้นความเรียบง่าย สะอาดตา และใช้งานง่าย (User-Friendly)
สไตล์การออกแบบ (Design Style): Modern, Clean, Glassmorphism, Mobile-First

3.1 สีประจำระบบ (Color Palette)
เราใช้สีโทนส้ม-แดง (สีอิฐ) ซึ่งเป็นสีประจำมหาวิทยาลัยขอนแก่น เป็นสีหลัก (Brand Colors)
- Brand 50 (#fef6f3): สีพื้นหลังอ่อนสุด สำหรับพื้นที่ที่ต้องการเน้นเล็กน้อย หรือ Hover state
- Brand 100 (#fcebe5): สีพื้นหลังอ่อน สำหรับการแบ่งแยกสัดส่วน Card หรือ Modal
- Brand 500 (#e56b40): สีหลัก (Primary Color) สำหรับปุ่มหลัก, ไอคอน, ลิงก์ที่ต้องการความโดดเด่น
- Brand 600 (#d95326): สีหลักเมื่อมีการกด (Active) หรือ Hover ลงบนปุ่ม
- Brand 900 (#732c14): สีเข้มสุด สำหรับข้อความที่ต้องการเน้นความเป็นแบรนด์

สีสนับสนุน (Semantic Colors)
- Success (สีเขียว): สำหรับการแจ้งเตือนสำเร็จ, สถานะการจองที่ยืนยันแล้ว, การเช็คอินสำเร็จ
- Danger (สีแดง): สำหรับปุ่มยกเลิก, การลบข้อมูล, การแจ้งเตือนข้อผิดพลาด
- Warning (สีเหลือง/ส้ม): สำหรับสถานะรอดำเนินการ, รอการยืนยัน
- Info (สีฟ้า): สำหรับข้อมูลทั่วไป, คู่มือ
- Gray (สีเทา): ใช้สำหรับตัวอักษร, กรอบ (Border), และพื้นหลัง (Background) เพื่อสร้างมิติ
  - Gray 50/100: พื้นหลังของหน้าแอปพลิเคชัน (App Background)
  - Gray 200/300: กรอบของกล่องข้อความ, เส้นแบ่ง (Dividers)
  - Gray 400/500: ตัวอักษรรอง (Secondary Text), Placeholder
  - Gray 700/800: ตัวอักษรหลัก (Primary Text), หัวข้อ (Headings)

3.2 การใช้ตัวอักษร (Typography)
- ฟอนต์หลัก (Primary Font): 'Inter', 'Noto Sans Thai', 'sans-serif'
- เหตุผล: Inter ให้ความรู้สึกทันสมัย เป็นสากล อ่านง่ายในภาษาอังกฤษ ส่วน Noto Sans Thai เข้ากันได้ดีในภาษาไทย ไม่มีการแตกหรืออ่านยากในหน้าจอขนาดเล็ก
- ขนาดตัวอักษร (Font Sizes):
  - H1 (Header 1): 24px - 32px (font-bold) สำหรับหัวหน้าหลัก เช่น "ระบบจองสนามกีฬา"
  - H2 (Header 2): 20px - 24px (font-semibold) สำหรับหัวข้อย่อย หรือชื่อสนาม
  - Body (เนื้อหา): 14px - 16px (font-normal) สำหรับรายละเอียดทั่วไป
  - Small (ขนาดเล็ก): 12px (font-medium หรือ font-light) สำหรับเวลา, ป้ายกำกับ (Labels)
- น้ำหนักตัวอักษร (Font Weights):
  - Normal (400): ข้อความทั่วไป
  - Medium (500): ปุ่มกด, เมนูนำทาง
  - SemiBold (600) / Bold (700): หัวข้อ, ตัวเลขที่ต้องการเน้น เช่น ราคา หรือ จำนวน

3.3 องค์ประกอบหน้าจอ (UI Components)
- Navigation Bar (เมนูนำทาง):
  - Mobile (ผู้ใช้ทั่วไป): เป็น Bottom Navigation Bar ยึดติดขอบล่าง (Fixed Bottom) พร้อมเอฟเฟกต์ Glassmorphism (พื้นหลังเบลอ bg-white/90 backdrop-blur-md) มีเมนู หน้าแรก, สแกนเช็คอิน (ปุ่มกลางนูนเด่น), การจอง, คู่มือ
  - Desktop / Admin: เป็น Sidebar หรือ Top Navigation
- Buttons (ปุ่มกด):
  - ปุ่มหลักมีความโค้งมนสูง (rounded-xl หรือ rounded-full) ทำให้ดูเป็นมิตร ลดความแข็งกระด้าง
  - มี Shadow อ่อนๆ (shadow-sm, shadow-md) และเพิ่ม Shadow เมื่อมีการ Hover
- Cards (การ์ดแสดงข้อมูล):
  - สนามกีฬาแต่ละแห่งแสดงในรูปแบบ Card ที่มีความโค้งมน มีเงา และเมื่อผู้ใช้นำเมาส์ไปชี้ (Hover) จะขยับขึ้นเล็กน้อย (Hover: -translate-y-1) พร้อมแอนิเมชันนุ่มนวล
- Forms & Inputs (ช่องกรอกข้อมูล):
  - ใช้ช่องกรอกขอบมน (rounded-lg หรือ rounded-xl)
  - กรอบสีเทาอ่อน (border-gray-200) เมื่อ Focus จะเปลี่ยนเป็นสี Brand (focus:border-brand-500) และมีเงา (focus:ring)

3.4 ประสบการณ์การใช้งาน (User Experience - UX)
- Feedback (การตอบสนอง): ทุกการกระทำของผู้ใช้ เช่น การกดปุ่ม การจองสำเร็จ หรือข้อผิดพลาด จะมีการตอบสนองอย่างชัดเจนผ่าน Toast Notification หรือ SweetAlert
- Loading States (สถานะกำลังโหลด): ระหว่างดึงข้อมูลจาก Backend ระบบจะแสดง Spinner สี Brand หรือ Skeleton Loading เพื่อไม่ให้หน้าจอดูนิ่งค้าง
- Error Handling (การจัดการข้อผิดพลาด): หากจองไม่สำเร็จ หรือกรอกข้อมูลผิด จะแสดงข้อความสีแดงเตือนใต้ช่องกรอก หรือแจ้งเตือน Pop-up พร้อมอธิบายสาเหตุชัดเจน เช่น "สนามนี้ถูกจองไปแล้วในเวลาที่คุณเลือก"

4. รายละเอียดฟังก์ชันการทำงานแยกตามผู้ใช้ (Features Breakdown by Role)
--------------------------------------------------------------------------------

4.1 สำหรับผู้ที่ยังไม่ได้เข้าสู่ระบบ (Guest)
- Landing Page (หน้าแรก):
  - แสดงโลโก้ KKU SportPass และคำอธิบายระบบสั้นๆ
  - ไม่มีแถบเมนู (Navbar) เพื่อป้องกันความสับสน
  - มีปุ่มเข้าสู่ระบบ (Login) ให้เห็นเด่นชัด
- Login Page (หน้าเข้าสู่ระบบ):
  - รองรับการล็อกอินด้วย Email และ Password (Local Strategy)
  - มีลิงก์สำหรับสมัครสมาชิก
- Register Page (หน้าสมัครสมาชิก):
  - กรอกชื่อ, อีเมล (รองรับเฉพาะโดเมน kkumail.com หรือ kku.ac.th ตามที่ตั้งค่า), รหัสผ่าน
  - มีการ Validate รหัสผ่านว่าต้องตรงกันทั้งสองช่อง

4.2 สำหรับผู้ใช้งานทั่วไป (นักศึกษา, บุคลากร)
- Dashboard (หน้าหลักผู้ใช้):
  - แสดงข้อมูลโปรไฟล์ย่อของผู้ใช้ (ชื่อ, บทบาท)
  - แสดงปุ่ม/การ์ดทางลัด เช่น การจองของฉัน, ค้นหาสนาม
  - แสดงรายการสนามกีฬาทั้งหมด แบ่งตามหมวดหมู่ (โซน Z1-Z4) หรือประเภทกีฬา
- Court Details & Booking (ดูรายละเอียดและจองสนาม):
  - ดูรูปภาพสนาม, ราคา, ความจุ
  - ดูตารางเวลาที่ว่าง/ถูกจองแล้วในแต่ละวัน
  - ผู้ใช้สามารถเลือก Timeslot ที่ต้องการและกดยืนยันการจอง
  - ระบบตรวจสอบว่าช่วงเวลาดังกล่าวซ้อนทับกับการจองอื่นหรือไม่
- My Bookings (การจองของฉัน):
  - แสดงรายการจองทั้งหมดของผู้ใช้
  - สถานะการจอง: รอดำเนินการ (PENDING), ยืนยันแล้ว (CONFIRMED), เช็คอินแล้ว (CHECKED_IN), ยกเลิก (CANCELLED), ไม่มาตามนัด (MISSED)
  - หากใกล้ถึงเวลาจอง (เช่น 10 นาทีก่อนถึงเวลา) จะมีปุ่มให้ "กดยืนยัน" เพื่อแสดงว่ามาใช้งานจริง
  - หากจองแล้วไม่มากดยืนยัน ระบบจะปรับสถานะเป็น MISSED และอาจถูกแบนการจอง (Blacklist) ในอนาคต
- Scan QR Code (สแกนเช็คอินหน้าสนาม):
  - เปิดกล้องมือถือสแกน QR Code ที่แปะอยู่หน้าสนาม (หรือที่แอดมินสร้าง)
  - ระบบตรวจสอบ Location (GPS) ว่าผู้ใช้อยู่ใกล้สนามในรัศมีที่กำหนดหรือไม่ (เช่น 30 เมตร) เพื่อป้องกันการเช็คอินทิพย์
- Manual (หน้าคู่มือการใช้งาน):
  - อธิบายขั้นตอนการจอง, กฎระเบียบ, ขั้นตอนการเช็คอิน
  - นำเสนอในรูปแบบ Step-by-step พร้อมรูปจำลองหน้าจอ (UI Mockups) ทำจาก CSS สวยงาม

4.3 สำหรับผู้ดูแลระบบ (Admin)
- Admin Layout:
  - ใช้ Sidebar ด้านซ้ายสำหรับการนำทาง (Navigation) แทน Bottom Nav
- Admin Dashboard / Courts (จัดการสนาม):
  - ดูรายการสนามทั้งหมด
  - สามารถ เพิ่ม/แก้ไข/ลบ สนาม (ชื่อ, ประเภท, โซน, พิกัด GPS, ราคา, ความจุ)
- Admin Timeslots (จัดการรอบเวลา):
  - ตั้งค่าเวลาเปิด-ปิด ของแต่ละสนาม และระยะเวลาแต่ละ Slot (เช่น สล็อตละ 1 ชั่วโมง)
- Admin Closures (จัดการการปิดสนามชั่วคราว):
  - ตั้งค่าปิดสนามล่วงหน้าเมื่อมีการปรับปรุงหรือมีกิจกรรมพิเศษ
  - ระบุวัน, สนาม, และเหตุผล ผู้ใช้จะไม่สามารถจองในวันเหล่านั้นได้
- Admin QR (พิมพ์ QR Code):
  - แอดมินสามารถดึงพิกัดสนาม (Lat/Lng) แล้วระบบจะ Generate QR Code ที่มีพิกัดเข้ารหัสอยู่
  - รองรับการปริ้นท์ (Print) เป็นโปสเตอร์ A4 สำหรับนำไปแปะหน้าสนาม
- Admin Users & Admins (จัดการผู้ใช้และแอดมิน):
  - เลื่อนขั้นผู้ใช้ทั่วไปเป็นแอดมิน หรือปลดแอดมิน
- Admin Settings (ตั้งค่าระบบ):
  - ปรับตั้งค่าตัวแปร (App Settings) ผ่านหน้า UI โดยไม่ต้องแก้โค้ด เช่น
    - ระยะเวลาให้กดยืนยันก่อนใช้งาน (เช่น 10 นาที)
    - รัศมี GPS ที่อนุญาตให้เช็คอินได้ (เช่น 30 เมตร)
    - โดเมนอีเมลที่อนุญาตให้สมัครสมาชิก

5. โครงสร้างฐานข้อมูล (Database Schema - PostgreSQL)
--------------------------------------------------------------------------------
ฐานข้อมูลแบ่งออกเป็น 7 ตารางหลักที่ทำงานสัมพันธ์กัน (Relational Database)

5.1 ตาราง users
- id (SERIAL, PRIMARY KEY): รหัสผู้ใช้
- name (TEXT): ชื่อ-นามสกุล
- email (TEXT, UNIQUE): อีเมล
- password (TEXT): รหัสผ่านที่เข้ารหัส (Hash)
- phone (TEXT): เบอร์โทรศัพท์
- role (TEXT): บทบาท ('user' หรือ 'admin')
- created_at (TIMESTAMP): วันที่สมัคร

5.2 ตาราง sport_types
- id (TEXT, PRIMARY KEY): รหัสประเภทกีฬา
- name_th (TEXT): ชื่อภาษาไทย (เช่น 'ฟุตบอล')
- name_en (TEXT): ชื่อภาษาอังกฤษ
- icon (TEXT): ชื่อคลาสไอคอน (เช่น 'fa-futbol')
- prefix (TEXT, UNIQUE): คำนำหน้า

5.3 ตาราง courts
- id (TEXT, PRIMARY KEY): รหัสสนาม (เช่น 'z1-1')
- name (TEXT): ชื่อสนาม (เช่น 'สนามฟุตบอล 50 ปี')
- type (TEXT): รหัสประเภทกีฬาอ้างอิง sport_types
- icon (TEXT): ไอคอนเฉพาะ
- price (TEXT): ราคา (เช่น 'ฟรี', '1,000 บาท/ชม.')
- capacity (INTEGER): ความจุ (จำนวนคนที่จองได้ต่อสล็อต)
- latitude (REAL): พิกัดละติจูด (สำหรับสแกนเช็คอิน)
- longitude (REAL): พิกัดลองจิจูด

5.4 ตาราง court_timeslots
- id (SERIAL, PRIMARY KEY): รหัสรอบเวลา
- court_id (TEXT, FK): อ้างอิง courts
- start_time (TEXT): เวลาเริ่ม (เช่น '08:30:00')
- end_time (TEXT): เวลาสิ้นสุด (เช่น '09:30:00')

5.5 ตาราง bookings
- id (SERIAL, PRIMARY KEY): รหัสการจอง
- user_id (INTEGER, FK): อ้างอิง users
- court_id (TEXT, FK): อ้างอิง courts
- booking_date (TEXT): วันที่จอง (YYYY-MM-DD)
- start_time (TEXT): เวลาเริ่ม
- end_time (TEXT): เวลาสิ้นสุด
- status (TEXT): สถานะ (PENDING, CONFIRMED, CHECKED_IN, CANCELLED, MISSED)
- pre_confirmed_at (TIMESTAMP): เวลากดยืนยันก่อนใช้
- checked_in_at (TIMESTAMP): เวลาสแกนเช็คอิน
- cancelled_at (TIMESTAMP): เวลายกเลิก
- missed_at (TIMESTAMP): เวลาที่ถูกตัดสิทธิ์
- checkin_lat (REAL), checkin_lng (REAL): พิกัดขณะที่สแกน
- checkin_distance_m (INTEGER): ระยะห่างจากสนามขณะสแกน (เมตร)

5.6 ตาราง court_closures
- id (SERIAL, PRIMARY KEY): รหัสการปิด
- court_id (TEXT, FK): อ้างอิง courts (ถ้า NULL คือปิดทุกสนาม)
- close_date (TEXT): วันที่ปิด (YYYY-MM-DD)
- reason (TEXT): เหตุผลการปิด

5.7 ตาราง app_settings
- setting_key (TEXT, PRIMARY KEY): คีย์ตั้งค่า (เช่น 'gps_radius_meters')
- setting_value (TEXT): ค่าของตั้งค่า (เช่น '30')
- label_th (TEXT): คำอธิบายภาษาไทย
- updated_at (TIMESTAMP): เวลาอัปเดต

6. เส้นทางการรับส่งข้อมูลทาง API (API Endpoints)
--------------------------------------------------------------------------------
ระบบใช้ RESTful API สำหรับการสื่อสารระหว่าง Frontend และ Backend รูปแบบ JSON
(ข้อมูลนี้คือโครงสร้างหลัก มีการป้องกันด้วย Middlewareตรวจสอบสิทธิ์: isLoggedIn, isAdmin)

6.1 หมวด Authentication (/api/auth)
- POST /api/auth/register : สร้างบัญชีผู้ใช้ใหม่
- POST /api/auth/login : เข้าสู่ระบบ (สร้าง Session/Cookie)
- POST /api/auth/logout : ออกจากระบบ (ทำลาย Session)
- GET /api/auth/status : ตรวจสอบว่าผู้ใช้ล็อกอินอยู่หรือไม่ พร้อมคืนข้อมูลโปรไฟล์ย่อ

6.2 หมวด Courts (/api/courts)
- GET /api/courts : ดึงรายการสนามกีฬาทั้งหมด (สำหรับผู้ใช้และแอดมิน)
- GET /api/courts/:id : ดึงข้อมูลสนามใดสนามหนึ่ง พร้อมรอบเวลา (Timeslots) และประวัติการจองของวันนั้น
- POST /api/courts : (Admin) เพิ่มสนามใหม่
- PUT /api/courts/:id : (Admin) แก้ไขสนาม
- DELETE /api/courts/:id : (Admin) ลบสนาม

6.3 หมวด Bookings (/api/bookings)
- POST /api/bookings : ส่งคำขอจองสนาม (ต้องเช็คเวลาซ้อนทับ และตรวจสอบการปิดสนาม)
- GET /api/bookings/my : ดึงประวัติการจองของผู้ใช้ที่ล็อกอินอยู่
- POST /api/bookings/:id/cancel : ยกเลิกการจอง
- POST /api/bookings/:id/confirm : กดยืนยันการจองก่อนถึงเวลา
- POST /api/bookings/checkin : ส่งข้อมูลสแกน QR Code (Lat, Lng) เพื่อเช็คอินเข้าสนาม
- GET /api/bookings/admin/all : (Admin) ดึงประวัติการจองของระบบทั้งหมด

6.4 หมวด Admin Settings (/api/admin)
- GET /api/admin/settings : ดึงค่า Setting ทั้งหมด
- PUT /api/admin/settings : อัปเดตค่า Setting
- GET /api/admin/users : ดูรายชื่อผู้ใช้
- PUT /api/admin/users/:id/role : เปลี่ยนสิทธิ์ (user <-> admin)

7. ความปลอดภัยและการตรวจสอบ (Security & Validations)
--------------------------------------------------------------------------------
1. รหัสผ่าน: ระบบไม่เก็บรหัสผ่านเป็น Plain Text แต่ทำการ Hash ด้วย Bcrypt (Salt rounds = 10)
2. การจองซ้ำซ้อน: Backend มี Transaction ควบคุม เมื่อส่ง Request จองเข้ามา จะมีการ Query ตรวจสอบว่า 'status' ที่เป็น PENDING, CONFIRMED, CHECKED_IN ในวัน/เวลา/สนาม นั้นมีกี่รายการ หากเต็มความจุ (Capacity) จะ Reject ทันที
3. ป้องกันการสแกนทิพย์: เมื่อสแกน QR Code หน้าสนาม ฟรอนเอนต์จะดึงพิกัด (Geolocation API) ของอุปกรณ์มือถือ แล้วส่งไปให้ Backend คำนวณระยะทาง (Haversine Formula) เทียบกับพิกัดจริงของสนาม ถ้าระยะห่างเกินกว่าที่ตั้งค่าไว้ (เช่น 30 เมตร) ระบบจะปฏิเสธการเช็คอิน
4. Session Hijacking: ใช้ HTTP-Only และ Secure Flag ใน Cookie (เมื่อใช้งานผ่าน HTTPS บน Vercel) เพื่อป้องกัน XSS เข้าถึง Session ID

9. การปรับปรุงและการขยายผลในอนาคต (Future Enhancements)
--------------------------------------------------------------------------------
1. ระบบแจ้งเตือน (Notifications):
   - เพิ่มระบบแจ้งเตือนผ่าน Line Notify หรือ Email เมื่อทำการจองสำเร็จ หรือแจ้งเตือน 1 ชั่วโมงก่อนถึงเวลาเข้าใช้สนาม

   - สำหรับสนามที่มีค่าใช้จ่าย ปัจจุบันเป็นการชำระที่หน้าสนาม ในอนาคตสามารถเชื่อมต่อระบบ PromptPay QR หรือ 2C2P เพื่อให้ชำระและยืนยันอัตโนมัติ

   - ฟีเจอร์ "หาเพื่อนเล่นกีฬา" ให้ผู้ใช้สร้าง Post เพื่อเชิญชวนผู้ใช้ท่านอื่นมาแชร์ค่าสนามหรือจัดทีม
4. ระบบสะสมแต้ม (Gamification):
   - ให้คะแนนเมื่อผู้ใช้มาเช็คอินตรงเวลา สามารถนำไปแลกของรางวัล หรือส่วนลดค่าสนาม

รายละเอียดสถานที่และประเภทกีฬาที่รองรับในระบบ KKU SportPass เพื่อให้เกิดความเข้าใจอย่างลึกซึ้งถึงสเกลของโปรเจกต์:

[สนามกีฬาหมายเลข Z1-001]
- ชื่อสนาม: สนามกีฬาอเนกประสงค์ โซน Z1 อาคารปฏิบัติการด้านกีฬา มหาวิทยาลัยขอนแก่น
- พิกัดทางภูมิศาสตร์ (GPS Latitude): 16.4401
- พิกัดทางภูมิศาสตร์ (GPS Longitude): 102.8201
- ประเภทกีฬา (Category): ฟุตบอล, บาสเกตบอล, วอลเลย์บอล, เทนนิส, แบดมินตัน, ฟุตซอล (Multipurpose)
- อัตราค่าบริการ (Pricing Rate): นักศึกษา ฟรี / บุคลากร ฟรี / บุคคลภายนอก 110 บาทต่อชั่วโมง
- ความจุสูงสุด (Maximum Capacity): รองรับผู้เล่นได้ 11 คนต่อ 1 ช่วงเวลา (Timeslot)
- สิ่งอำนวยความสะดวก: ห้องน้ำ, ห้องอาบน้ำ, ตู้ล็อกเกอร์, ที่จอดรถ, ไฟส่องสว่าง (เปิดอัตโนมัติตามช่วงเวลาการจอง)
- กฎระเบียบข้อบังคับ:
  1. โปรดแต่งกายด้วยชุดกีฬาที่เหมาะสมและสุภาพ
  2. สวมรองเท้าผ้าใบหรือรองเท้ากีฬาเฉพาะทางเพื่อป้องกันพื้นสนามเสียหาย
  3. ห้ามนำอาหารและเครื่องดื่ม (ยกเว้นน้ำดื่มขวด) เข้ามาในบริเวณพื้นที่แข่งขัน
  4. ผู้เข้าใช้บริการต้องทำการเช็คอินด้วย QR Code ผ่านแอปพลิเคชัน KKU SportPass เท่านั้น
  5. หากพบการละเมิดกฎ ระบบจะทำการบันทึกและพิจารณาระงับสิทธิ์การจองในครั้งถัดไปเป็นเวลา 30 วัน
